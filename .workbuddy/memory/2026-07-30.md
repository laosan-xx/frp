## 如何快速读懂 frp 项目（19:15，方法论沉淀）
- **核心抽象**：frp = 一条常驻控制连接（跑 msg 信令：Login/NewProxy/Ping/ReqWorkConn）+ 按需建立的工作连接（搬运真实 TCP/UDP 流量）。两个 `Control`（`client/control.go` 与 `server/control.go`）是理解全项目的关键。
- **推荐阅读顺序**：cmd 入口 → `pkg/config/v1/*` → `pkg/msg/msg.go` → `client/{service,control_session,control,connector}.go` → `server/{service,control}.go` → `server/proxy/{proxy,tcp}.go` + `client/proxy/{proxy,general_tcp}.go` → `pkg/{auth,proto/wire,transport/message}` → `pkg/config/load.go` → `test/e2e/v1/basic/tcp.go`。
- **开发四习惯**：① 改代理先看 `proxy.go` 接口与 `proxyFactoryRegistry`；② 加配置先改 `v1/*` 结构体（含 json tag）再走 `load.go`；③ 加 C/S 通信先改 `pkg/msg/msg.go` 并注册 handler；④ 验证优先 `make e2e` 写/改 E2E 用例。
- 已向用户用两张架构/数据流图（控制连接 vs 工作连接、TCP 请求端到端 7 步）讲解，并给出 `pkg/` 重点包速查。

## 21:51 ✅ 真根因：run_socks 退出码是假的（xray 其实起来了）
- **决定性证据**：21:41 版的 `sh -x` 跟踪（用户贴回）最后几行——
  - `+ /tmp/etc/passwall/bin/xray run -c /tmp/etc/passwall/url_test_ip_<secID>.json`（xray **已成功启动**）
  - `+ set_cache_var node_<secID>_socks_port 44199`（端口已写入缓存）
  - `+ '[' xray '!=' xray ']'`（脚本**最后一行** `[ "$type" != "xray" ]` 对 xray 节点求值为**假** → 整个 `run_socks` 返回 exit 1）
- **根因（确定）**：shell 脚本/函数的退出码 = 最后一条命令的退出码。app.sh `run_socks` 末尾的 `[ "$type" != "xray" ]` 判断对 xray 节点为假 → 退出码 1，**但代理实际已成功启动**。我们此前 `if err != nil` 一拿到非零退出码就放弃，把"成功的启动"误判为"起代理失败"，从没走到检测端口那步。这解释了所有"exit status 1 但诊断里 xray 明明起来了"的矛盾。（注：21:41 去掉 `CONFIG=passwall` 与 flag 隔离均非根因，但保留无害。）
- **修复**（`client/command_builtin.go` `cmdURLTestNode` + diag 第 9 段）：**不再相信 run_socks 退出码**，跑完后一律 `waitPortOpen` 检测端口——端口开了即代理已起，直接测 IP；只有端口 10s 内不监听才算真失败（此时附 `traceRunSocks` 的 sh -x 跟踪）。
- **教训（可复用）**：① 对 passwall `app.sh` 这类脚本，**退出码不可信**，要以"端口是否监听/进程是否在"等实际效果为准；② 破解"错误进 syslog、stdout 空"黑盒的最快手段是对同一调用跑 `sh -x ... | tail -N`。
