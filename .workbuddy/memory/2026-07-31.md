## 修复：并发测速一个报错（端口 TOCTOU 竞态）
- 根因：`testNode` 的出口 IP 探测用 `getFreePort()` 取端口后**立即关闭监听**把端口还回。两个测速按钮同时点 → 两个 goroutine 抢到同一端口 → 后起的 `run_socks` 绑定失败 → “代理未在10s内监听” 报错。
- 修复：新增 `startEgressProbeProxy(secID, timeout)`，用全局 `tempProxyMu` 串行化“预留端口→起 run_socks→waitPortOpen 确认监听→才释放预留监听”这段握手，期间持有 `net.Listen` 监听，确保端口不会被其他并发测速抢走。flag 仍用 `url_test_ip_<secID>`（与官方 test.sh 的 `url_test_<secID>` 区分）。
- `cmdURLTestNodeDiag` 仍用 `getFreePort`（诊断场景，单发，不影响）。

## 修复：节点测速“谁先点谁失败 + 延迟不对劲”（命令串扰）
- 用户现象：两个节点前后分别点“测试”，第一个点必失败；没失败的那个延迟还不对。
- 根因：`server/control.go` 的 `SendCommandToClient` 每次都用 `ctl.OnServerCommandResp(onResp)` **重新注册** `ServerCommandResp` 处理器，**直接覆盖**上一次回调。两个请求并发时：请求A注册回调A→处理器=A；请求B注册回调B→处理器=B（A被覆盖）。frpc 回 A 的响应→处理器调 B→进 respChB；回 B 的响应→又进 respChB(缓冲1丢弃)。结果 respChA 永远拿不到→请求A超时失败；respChB 拿到的是 A 的响应→延迟是第一个节点的。完全对应现象。
- 修复（按请求ID关联响应，而非单回调覆盖）：
  - `pkg/msg/msg.go`：`ServerCommand` / `ServerCommandResp` 新增 `RequestID` 字段（json 标签；V1=golib/msg/json、V2=json.Unmarshal，两条线都 JSON，自动走线上）。
  - `client/control.go` `handleServerCommand`：回响应时把 `inMsg.RequestID` 拷进 `resp.RequestID`。
  - `server/control.go`：`Control` 加 `pendingServerCmdsMu` / `pendingServerCmds map` / `serverCmdHandlerOnce`；`ControlManager` 加 `serverCmdSeq uint64`。`SendCommandToClient` 生成 `reqID` 写入 `cmd.RequestID`；`OnServerCommandResp(reqID, fn)` 用 `sync.Once` 仅注册一次处理器，按 `resp.RequestID` 路由到对应回调并删除（未知 reqID 仅告警）。删除原未注册死代码 `handleServerCommandResp`（日志移植进新 handler）。接口 `SendCommandToClient` 签名未变，调用点无改动。
- 节点测速超时改 10 秒：`server/http/controller_v2.go` 的 HTTP 等待超时改为按命令区分——`url_test_node`/`url_test_device` 用 10s，其它远程命令仍 30s（错误文案随超时动态化）。
- frpc 侧收紧耗时以匹配 10s：`command_builtin.go` 的 `detectEgressIPVerbose` warmup `-m 6→4`、候选 `--max-time 6→4`；`testNode` IP 探测重试 3×2s→2×1.5s。确保整体能在 10s 内返回。
- 验证：`go build ./server/... ./client/... ./pkg/msg/...` exit0；`go vet` 三个包 exit0；`go test -run xxx` 两个包测试可编译。
